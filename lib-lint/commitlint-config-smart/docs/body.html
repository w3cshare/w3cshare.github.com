提交消息正文指南 ​

提交消息正文是提交主题行之后的详细说明部分，用于提供更多关于变更的详细信息。虽然不是所有提交都需要正文，但对于重要或复杂的变更，正文是必不可少的。

为什么需要正文？

正文让其他开发者（和未来的你自己）能够更好地理解变更的上下文、原因和实现方式，大幅提高代码可维护性。

正文的位置 ​

在提交消息格式中，正文位于主题行之后，中间空一行：

<type>(<scope>): <subject>

<body>

<footer>

何时使用正文 ​

以下情况建议使用正文：

  1. 复杂变更：实现了复杂的功能或修复了复杂的问题
  2. 重大改动：包含破坏性变更（Breaking Changes）
  3. 设计决策：需要解释为什么选择了特定实现方法
  4. 多方面变更：一次提交包含多个相关联的变更
  5. 复杂问题修复：修复了难以理解或重现的bug

避免过于简单的正文

如果你的正文内容仅仅是重复了主题行的信息，那么可能不需要正文。正文应该提供额外的有价值信息。

正文的格式规范 ​

基本规则 ​

  1. 使用空行分隔段落：增加可读性
  2. 每行限制72个字符：确保在各种终端和工具中正确显示
  3. 使用完整句子：包含主语、谓语和宾语
  4. 使用祈使句：与主题行保持一致的语气
  5. 提供上下文：解释变更的背景和原因

中文正文规范 ​

对于使用中文的项目，正文应遵循以下额外规范：

  1. 简体中文：统一使用简体中文
  2. 避免使用缩写：除非是广泛接受的技术缩写
  3. 保持标点符号一致：统一使用中文或英文标点
  4. 段落结构清晰：可使用项目符号或数字列表增强可读性

中英混排规范

当在中文正文中出现英文单词、数字或代码片段时，在中英文之间添加空格，例如：

  • 实现了 OAuth 2.0 认证功能
  • 修复了 Safari 浏览器下的兼容性问题
  • 优化了 useEffect 钩子的依赖项

正文内容指南 ​

一个完整的提交消息正文应回答以下问题：

  1. 为什么需要这个变更？
  2. 它如何解决问题？
  3. 这个变更对系统有什么影响？
  4. 有哪些需要注意的限制或边界条件？
  5. 相关的问题或任务编号是什么？
正文检查清单

使用以下问题检查你的正文是否完整：

  • [ ] 是否解释了变更的背景和原因？
  • [ ] 是否描述了解决方案或实现方法？
  • [ ] 是否提及了潜在的影响或限制？
  • [ ] 是否链接了相关资源（如任务、讨论、文档）？
  • [ ] 是否描述了测试方法或结果（如适用）？ :::

有效的正文示例 ​

功能添加示例 ​

feat(auth): 添加谷歌OAuth登录功能

实现了基于OAuth 2.0协议的谷歌账号登录功能，使用户可以通过谷歌账号快速注册和登录系统。

主要包括：
1. 集成谷歌OAuth 2.0 API
2. 添加授权回调处理
3. 用户信息自动关联和账号创建
4. 权限验证和令牌刷新机制

该功能大幅简化了用户注册流程，预计可提高注册转化率约15%。

相关任务: #TASK-123

问题修复示例 ​

fix(database): 修复高并发下连接池耗尽问题

在高并发场景下，数据库连接未能正确释放，导致连接池资源耗尽，系统响应变慢并最终超时。

问题原因：
- 事务提交后连接未正确关闭
- 异常处理路径中缺少连接释放代码
- 连接池配置不合理

解决方法：
1. 添加try-finally确保连接总是被释放
2. 调整连接池大小和超时设置
3. 增加连接泄漏检测和自动回收机制

性能测试显示该修复在高峰期将系统响应时间从2.5s降至0.8s。

修复: #BUG-456

重构示例 ​

refactor(components): 重构表单组件以提高复用性

将原有的紧耦合表单组件拆分为更小的可组合组件，使其更容易被复用和测试。

重构内容:
- 抽取表单项为独立组件
- 实现自定义Hook管理表单状态
- 分离表单验证逻辑
- 添加组合模式支持嵌套表单

此次重构不改变现有功能，但大幅降低了代码复杂度（从循环复杂度15降至4）
并减少了代码重复（减少约120行重复代码）。

相关: #TECH-789

链接最佳实践

  • 使用完整URL而不是相对路径
  • 为URL添加简短描述说明链接内容
  • 将重要链接单独成行以增强可读性

自动化配置 ​

您可以在commitlint.config.js中配置对正文的检查：

js
module.exports = {
  extends: ['@company/commitlint-smart'],
  rules: {
    'body-leading-blank': [2, 'always'],
    'body-max-line-length': [2, 'always', 72],
    'body-case': [0, 'always', 'lowerCase'],
  },
}

团队最佳实践 ​

根据实际项目经验，我们总结了以下正文编写的最佳实践：

  1. 使用模板：为常见提交类型创建模板，减少格式错误
  2. 增量编写：先完成代码再编写提交信息，确保描述准确完整
  3. 同行评审：重要提交的消息也应该经过评审
  4. 参考历史：参考项目中高质量的提交消息作为范例
  5. 避免过度详细：提供足够信息，但避免过于冗长的描述

不要在正文中包含敏感信息

避免在提交正文中包含密码、密钥、个人身份信息等敏感数据。

小结 ​

一个好的提交消息正文：

  • 解释变更的原因和影响
  • 提供足够的上下文理解变更
  • 记录重要的设计决策
  • 链接相关资源和参考信息
  • 帮助未来的开发者理解代码演化历史

记住：编写详细的提交消息正文是对未来自己和团队成员的尊重，它将在代码审查、故障排除和功能理解方面节省宝贵的时间。
